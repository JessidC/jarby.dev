SIESA's support chat ran on a third-party chatbot whose answers we couldn't measure or control. I built an engine the company owns. It now answers about 1,000 conversations a day across 15 ERP modules.

It started with the data

I studied 90 days of production conversations, more than 55,000 chats, to see what customers actually went through. There was no way to tell whether an answer was right, and the model and the sources sat with the vendor, so we couldn't enforce a rule against invented answers. The handoff to a person needed a redesign as much as the bot did.

I took that to leadership as a plan with six decisions ranked by impact and cost. The main one was to build our own engine and redesign the handoff at the same time.

The engine

  • No framework in the request path

    Python and FastAPI straight on the model API, so every millisecond and every token can be traced.

  • Claude on AWS Bedrock

    SIESA already ran on AWS, so billing and permissions stayed in the account it had. Sonnet answers, Haiku rewrites follow-ups and reads scanned pages.

  • Retrieve wide, rerank narrow

    pgvector search filtered by ERP module, then Cohere Rerank keeps the five passages the model reads.

  • Checked before it goes out

    Every citation has to exist in what was retrieved. A number that isn't in the sources sends the chat to a person.

  • Rules before the model

    About 170 deterministic rules handle greetings, risk and requests for a person before any LLM call.

  • Same contract as the old bot

    The support portal didn't change. Each module could switch to the new engine, or back, with one setting.

One module at a time

  1. Before launchShadow run772 real conversations, answers hidden. An independent judge preferred the new engine 44% of the time, the old one 40%.
  2. Wave 1PayrollThe busiest module first. Customers kept the same chat window.
  3. Wave 2FinancialOne module per release window.
  4. Wave 3Commercial and ZeusPlus e-invoicing, accounting and the rest.
  5. Now15 ERP modulesAbout 1,000 conversations a day.

No module switched without a golden-set score from an LLM judge, smoke tests on the live chat and a rollback that takes one setting.

The fix was in the content

Hybrid retrieval looked like the obvious upgrade. I built it, measured it twice on real customer queries and switched it off. In Spanish, a keyword query behaves like an AND and empties the candidate pool, so it recovered 0 of 5 failing cases, and every retrieval variant landed within 3.6 points of the others. On the English Odoo docs in rag-eval-bench the same technique won by 12.5 points. Same idea, opposite result, which is why every change gets measured on its own data.

So the effort went to the content. I reprocessed 1,027 documents with multimodal OCR, isolating the fifth of the index an earlier OCR had damaged, and built a loop so the content keeps growing on its own.

Every change now ships the same way. A golden set per module scored by an LLM judge, an A/B replay on real traces and a significance test before and after. I rebuilt that method in the open as rag-eval-bench.

It learns from the agents every week

When the engine hands a chat to a person, the agent's answer is the best signal of what it was missing. A separate pipeline turns those answers into new knowledge, with an expert deciding what goes in.

  1. An agent closes the chatResolutions reach the engine through a data bridge from the support portal every 30 minutes.
  2. Only real gaps continueHandoffs caused by staffing, frustration or risk are dropped before any model call.
  3. A judge reads the agent's turnsIt comes from a different model family than the one that answers. It rebuilds the question and the reusable answer with its evidence, and rejects what can't be documented, like "open a ticket".
  4. Compared with what the engine knowsAlready covered is skipped. A repeat adds demand to the pending item. An answer that contradicts indexed content is flagged as outdated.
  5. An expert approves or edits itFrom the curation console. Approved answers are served right away, with no reindex.

What it never does

  • Publish anything an expert hasn't approved
  • Let the answering model grade its own work
  • Pay to judge the same content twice, thanks to a content fingerprint
  • Learn from handoffs that were a staffing problem

About 30 to 60 minutes from a closed chat to a candidate in the queue.

50%→40%

Human escalation in Commercial, in round numbers, after the loop started feeding it.

It adds about 150 approved answers a week for roughly US$10 a month in model cost, and 44 agent accounts curate from the console with roles and permissions per module. It is the main reason the engine keeps getting better between releases. I rebuilt it in the open as support-learning-loop.

Public code

rag-eval-bench

A bench that decides whether a RAG change ships. Golden set with questions the docs can't answer, an LLM judge, a validator that catches invented citations and numbers, and a paired McNemar test behind a CI gate. It runs on the public Odoo 18 docs.

What it found. Hybrid retrieval beat dense by 12.5 points, p = 0.02. A reranker added 1.4 points and pushed p95 latency from 2.5 s to 8.3 s, so it doesn't ship.

support-learning-loop

The improvement loop from the SIESA engine, rebuilt on public data. A support bot hands chats it can't solve to people. A judge from another model family turns the agents' answers into candidate entries, a grounding check rejects anything the agent didn't say, and an expert approves each one before the bot can use it.

In production

Jarvis

The judge of the support service. Every day it reads each conversation and decides who resolved it, the AI, an agent or no one, with the same rule for both. At closing it types the ticket, replacing a classifier whose attribution didn't hold up against a ticket-by-ticket audit.

It grew out of the conversation judge I already ran on the RAG's data. Same engine, now orchestrated in LangGraph with parallel judges, PostgreSQL checkpoints and pauses for human review. Its results feed Power BI and a daily report the support team reads in Teams.
